1//! Distributed multi-device identity and authorization for Krikos.
2//!
3//! `krikos-identity` keeps a stable account identity separate from replaceable endpoint,
4//! controller, and application-device keys. Its default-feature core verifies canonical v1 wire
5//! objects, projects an append-only account-control history, detects forks, evaluates structural
6//! capabilities, and returns explicit effects without reading a clock, network, database, or
7//! random-number source.
8//!
9//! # Authority model
10//!
11//! An authenticated Krikos endpoint proves control of one transport key; it is an authorized
12//! account device only after that key is matched to an active device at a verified checkpoint.
13//! Likewise, transparency providers can retain, timestamp, and prove inclusion of authorized
14//! records but cannot create account authority. [`AccountState`] applies each transition under the
15//! exact previous policy and admission evidence, while [`AccountStore`] implementations retain the
16//! canonical source history and idempotent operational effects.
17//!
18//! Offline decisions are always relative to a named checkpoint and epoch. Callers that require
19//! current status must supply policy-sufficient provider evidence and explicit verifier time;
20//! absence of that evidence is not converted into a global-validity claim. Conflicting histories
21//! enter a forked lifecycle and require an explicitly authorized resolution.
22//!
23//! # Features
24//!
25//! - The default feature set is empty and contains the runtime-independent, deterministic protocol
26//!   core. APIs that accept caller-owned randomness remain available here.
27//! - `fs-store` enables the redb-backed account source, checkpoint, and effect store.
28//! - `provider-store` enables redb-backed provider generations, auditing, and operational journals.
29//! - `net` enables bounded Tokio/Krikos framing and protocol adapters.
30//! - `os-rng` enables only convenience APIs that obtain fresh secrets from the operating system.
31//!
32//! Applications normally start with [`AccountGenesis`], reconstruct or load an [`AccountState`],
33//! verify and commit [`AuthorizedEvent`] values through an [`AccountStore`], and make application
34//! decisions only from a verified checkpoint/capability basis. All public wire decoding goes
35//! through the bounded, canonical [`CanonicalWire`] contract.
36//!
37//! The exact v1 serialization profile and codepoints are documented in the crate README. Provider
38//! recovery/compaction procedures and the security/deployment guide live in the crate's `docs/`
39//! directory. This crate is not yet a stable protocol release; external audit, independent
40//! interoperability, and production provider diversity remain explicit release gates.
